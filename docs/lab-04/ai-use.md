## 3. My Reflection

**Specification agent vs coding agent.** I used the agent in two different roles. For Issue 1 it worked as a specification agent: it read the handout, the Lab 3 contract, and the existing code, and turned them into FR, BR, AC, and test IDs before any Lab 4 code existed. That contract paid off. Every later issue started from "which rows of tests.md does this issue own?", the tests were written first and seen failing, and reviewers could check a PR against a written rule instead of my intent. The contract was not perfect, though. While coding, the agent found places where it contradicted itself or the handout: user-account cards whose drill-downs could never match their counts, a list item missing the fields the UI spec asked it to show, and a Requester cancel that would have edited Actions Taken. The useful habit was that it stopped and asked, and every answer became a recorded decision (D-11 to D-19) instead of a silent change. The specification agent is fast at producing a complete-looking contract; the coding agent is where that contract actually gets tested.

**What was verified by hand.** "Tests pass" was not taken on trust. My peer reviewer re-ran the suites on a fresh database, which showed that the one local failure (MIGR-02) came from my dev data, not the code. The reviewer also drove the live API by hand to confirm the resolution gate, the 403s, and the read-only history. The screenshots were checked by eye at all three widths, which caught problems no assertion did: a squeezed Description column, words breaking mid-word on tablet, Bootstrap-blue links, and a nav that wrapped and later overflowed. Claims were checked against the database instead of assumed. For example, a "duplicate action" was really the hidden mobile copy of one row, and the README's demo accounts did not hold the data the first draft claimed.

**Where the AI had to be corrected.** Three times a reviewer caught a real defect that the agent's own tests had missed: the documented rollback failed with P3012 because the test bypassed Prisma (PR #66); a Requester cancel recorded the Requester as the person who changed an Action Taken, and two Requester writes skipped `expectedVersion` (PR #69). The agent also caught some of its own mistakes: a regression test that passed even without the fix (13 rows were too few, so it raised the count to 60), a test proxy that could pass for the wrong reason, a search that silently skipped a whole spec file, and a cleanup check that was written too late to be seen failing, which it reported rather than hid. The lesson I take from this sprint is that an AI agent writes plausible, passing code quickly, so my job shifts to deciding what "correct" means, writing that down first, and checking the evidence — fresh databases, screenshots, and the database itself — rather than the agent's summary.

**What I would do differently.** First, I would ask the specification agent to check the contract against itself before any code is written. The contradictions found in Issue 7 (drill-downs that could never match their cards, list items missing fields the UI needed) could have been caught in Issue 1, when changing the contract cost nothing. Second, I would make tests go through the same tools a real user runs. The rollback test passed with raw SQL while the documented Prisma command failed, so a test is only as good as the path it exercises. Third, I would plan the seed data around the demo and the screenshots from the start, instead of finding out at the end that some accounts had nothing to show. Overall, Lab 4 showed me that working with an AI agent is less about typing good prompts and more about setting up the rules, the contract, and the checks it works inside, and then reviewing its work as carefully as I would review a teammate's.
